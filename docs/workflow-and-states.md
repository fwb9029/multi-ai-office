# 工作流、结果契约与状态

核对日期：2026-11-16。

本仓库只有方案文档和合成示例，不包含原工程源码或运行数据。接口、字段和文件名用于说明已经实现过的原型行为，不能据此直接运行原工程命令；当前没有通用安装包。

## 一次任务如何经过系统

1. **Codex 整理需求。** 确定目标、必要输入、交付格式和核对标准，挑选本次实际需要传递的规则，不整份上传私人资料或 Skill。
2. **形成计划。** 原型计划包含 `title`、`requirement` 和 `steps`；每步有 `worker`、`title`、`instruction`。允许的 worker 为 `doubao`、`workbuddy`、`deepseek`。原型接受一至八步，按数组顺序执行。
3. **保存后派发。** 队列先持久化任务和步骤状态，再调用相应适配器。同一队列一次只执行一个步骤，跨任务也不并发占用桌面。
4. **收回与结构检查。** 适配器读取本轮实际正文或成果文件，核对回执和归属。界面显示“完成”、一句回复或文件存在，单独都不能证明任务成功。
5. **交给下一步。** 原型读取已收回的文本类成果，连同来源步骤和文件名作为下一步材料传递；不是只传一个对方无法读取的本机路径。文件任务则在独立目录内读取明确提供的输入。
6. **Codex 内容验收。** 所有步骤收回后，Codex 读取正文、检查文件和关键计算，记录接受或需修改。需要改稿时，用新任务携带前稿和修改意见，保留原成果。

步骤五不要求步骤四的内容已经审稿通过。原型会先做结构与归属检查，再继续计划，最后统一等待内容验收。若业务要求“先审稿再交给下一工具”，应拆成两个计划，由 Codex 在中间明确审核。

## 输入和输出契约

| 对象 | 关键字段或文件 | 含义 |
|---|---|---|
| 总计划 | `title`、`requirement`、`steps` | 用户目标与已经决定的执行顺序 |
| 普通步骤 | `worker`、`title`、`instruction` | 指定一个执行工具及它负责的部分 |
| Harness 步骤 | 另加 `billing.approvalId` | 引用有效的单次授权；每个计划最多一个 Harness 步骤 |
| 豆包结果 | `final.md`、`result.json` | 非空正文，回执为 `completed`、`doubao_web`、`api_used:false`；正文与回执需一致 |
| WorkBuddy 输入 | `input.json` | 本次任务编号、随机 `challenge`、需求、步骤说明及前序材料 |
| WorkBuddy 回执 | `job_id`、`challenge`、`summary_cn`、`artifacts` | 编号和校验码应匹配本次输入；成果清单只列本目录普通文件，并包含 `final.md` |
| Harness 结果 | `final.md`、`result.json` | 非空最终正文；回执需确认 `deepseek_harness_desktop` 路线及 `existing_balance_user_approved` 来源 |

合成示例中的标识和内容只能用于理解结构，不能当作真实结果、有效费用授权或已发生的业务记录。复现时每项任务使用新的编号、随机校验码和成果目录。

成果清单需要防止绝对路径、上级目录跳转、符号链接和硬链接，设置合理的文件数量及大小限制。前序成果中的文字属于待处理材料，不能因被下一步读取就获得修改系统规则、扩大权限或另行派工的资格。

## 业务状态与内容验收

| 任务状态 | 含义 | 后续动作 |
|---|---|---|
| `queued` | 计划已保存，尚未执行 | 由串行队列取出 |
| `running` | 当前正在执行步骤 | 等待对应适配器收回结果 |
| `awaiting_review` | 结果已收回，内容尚未最终验收 | Codex 核对实际成果 |
| `completed` | 已记录验收通过 | 向用户交付 |
| `needs_attention` | 执行不确定、异常或验收要求修改 | 核查原任务与实际成果，决定后续处理 |
| `failed` | 已核查并保留为未完成的旧尝试 | 不覆盖旧证据，必要时建立新任务 |

`content_reviewed:false` 表示内容还没有通过验收。工具回执的 `completed` 只表示该适配器已经收回结果，不等于总任务的 `completed`，也不代表内容正确。

验收不通过会把该任务标为 `needs_attention`；执行异常还会暂停队列。这两种来源应在说明中区分，不能把每个“需要处理”都解释成连接故障。

## 异常恢复：先核查，再决定

- 发送前检查草稿、正在执行的任务、目标页面和本次工作目录；发现冲突时保留现场，不覆盖输入。
- WorkBuddy 在单次发送前持久化派发记录；Harness 先排他消费授权，再发送。已存在记录不能作为自动重发的理由。
- 超时或无法确认结果时，保存不确定状态并暂停后续执行。平台任务可能仍在运行；“本地等待结束”不等于“平台已经失败”。
- 重启时，原型把未确定的运行中或排队任务转为待核查，不盲目继续派发。
- Codex 检查原界面、回执和成果，记录恢复理由。恢复队列时保留旧尝试为失败，未执行的后续步骤可标为 `skipped`；需要重新尝试时使用新任务、新目录，不能复用原派发记录。
- 回执归属检查和内容验收分别记录。即使超时后找到了同一任务写回的文件，也必须核对归属与质量，不能直接改成成功。

上述防重复与暂停行为有离线检查和真实异常处理记录；具体平台是否幂等、长任务是否稳定，并未因此获得保证。

## 费用授权独立于任务计划

原型保存 `freeFirst:true`、`paidFallback:false`。免费路线失效时先核查并说明，不自动改走付费模型。

Harness 当前只接受明确批准的现有余额小测试。授权记录限制用途、有效期、提示长度和一次消费；执行器负责核对并排他消费。计划中的授权编号不是凭空取得收费权限的方法，失败也不会自动恢复已消费授权。当前桌面路线没有硬 token 或总价上限。

WorkBuddy 使用现有账号，不代表它不消耗积分；豆包网页免费范围也由账号规则决定。新的登录、验证码和必要费用决定仍由使用者本人完成。

## 办公室状态与任务状态分开

办公室继续使用 `busy`、`idle`、`attention`、`offline`、`unknown` 五种状态码，通过显示标签解释当前阶段：

| 场景 | 状态与显示 |
|---|---|
| 工具步骤正在执行，连接已确认 | `busy`，工作中 |
| 豆包成果已收回、等待验收且连接正常 | `idle`，已交稿 |
| 其他工具成果已收回、等待验收且连接正常 | `idle`，已收回 |
| 成果收回后连接断开 | 仍为 `offline`；摘要可以说明已有成果，不能把它显示成已连接 |
| 工具执行中连接未确认，或执行异常暂停 | `attention`，说明需要核查的原因 |
| Codex 已明确空闲，但队列存在待验收任务 | `attention`，待验收 |
| Codex 已明确空闲，但队列已暂停 | `attention`，任务暂停 |
| Codex 有明确忙碌活动 | `busy`，工作中 |
| 活动或连接情况无法确定 | `unknown`，待同步 |

运行、异常和断线不被“已收回”标签覆盖。正常待验收也不应显示成仍在生成。显示层本身不提交 review，不消费余额，不触发新任务。

## Codex 活动来源

跨聊天来源使用 `UserPromptSubmit`、`Stop`、`Interrupt`、`SessionEnd` 四类 Hook，按会话和轮次匹配活动。一个会话结束不能结束另一个；同轮次继续响应时应恢复忙碌。Hook 的结束事件只是响应边界，不是业务验收。

范围限本机同一用户配置下、正常信任了这些 Hook 的会话。接收者必须自行授权并通过正常信任审核，不复制另一台电脑的全局配置或信任记录。启用前已在进行的活动可用官方状态快照作有限时效的起点，不伪造开始事件。

Hook 没有过程心跳。长任务静默、事件缺失、记录损坏等情况会转为待同步；原型使用十五分钟静默边界，不凭超时推断空闲。原单条来源只读取明确绑定的一份会话记录，作为已知忙碌兜底，不扫描其他聊天正文。

任务服务的持久化记录可能包含需求与成果，办公室接口则只输出必要的状态和简短摘要。两者都不应被直接当作公开仓库示例导出。
